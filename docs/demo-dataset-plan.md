# Demo dataset expansion plan

Why: the captured Lumen fixtures hold one day of attributed traffic (539 viewers on the biggest test, under 80 on the others), no per-day series, one country breakdown and four tests. Good enough to prove the referee, thin for a demo. This plan grows a synthetic, Adapty-shaped dataset that the mock store can serve instead, without touching the real Lumen app (re-seeding is forbidden by the rules).

Ground rules
- Synthetic only. Nothing is written to Adapty. The expanded set lives in `backend/referee/adapty/fixtures_expanded/` and is generated by `backend/scripts/expand_seed.py` with a fixed random seed, so it is reproducible and reviewable.
- Same shapes as the real API answers (list, detail, metrics rows, metrics tree with levels root > variation > segment > screen > product, metrics total, flows, placements, segments, products, analytics chart and conversions).
- The captured set stays untouched; `ADAPTY_FIXTURES=captured|expanded` picks the set.
- Every referee verdict code should be reachable in the expanded set so the demo can show each state.

Source data

The seed repo ships the dataset that was replayed into Lumen: `data/offline/users.csv.gz` (50,000 users, installs 5 Jul to 2 Nov 2026, about 420 a day, with platform, country, placement, flow and A/B test assignment) and `data/offline/transactions.csv.gz` (29,794 rows: trials at price 0 with `offer=free_trial`, paid periods, renewals as further `seq` rows, refunds). Copied to `backend/scripts/data/` so the generator runs without the seed repo.

Facts that shape the expansion (from `expand_seed.py analyze`)
- Onboarding test: 13,798 users on weekly-first vs 13,771 on annual-trial; lifetime payers 3,007 vs 1,486; revenue $110k vs $59k. Over four months the weekly-first arm really wins; on day one the trial arm shows zero.
- Main NA test: 2,100 vs 2,085 users; the lifetime anchor arm earns $35k vs $19k.
- Settings test: 1,785 vs 1,722 users; both arms earn about $19k to $21k, a genuine no-difference case.
- Trial to paid: annual 7-day trials convert at 34%, weekly 3-day trials at 82% (first paid week counts).
- Only placement, flow and test assignment are attributed; no views per screen, so screen funnels stay synthetic.

Log
- Iteration 1 (7 Nov 2026 evening): captured set measured; offline dataset profiled; generator skeleton (`analyze`, `build`) and manifest-based fixture loading added; `ADAPTY_FIXTURES` switch wired through settings, client and health.
- Iteration 2: the generator now aggregates the offline users and transactions into Adapty-shaped answers. The dataset is shifted so its last install lands on the demo clock (`--now`, default 7 Nov 2026 17:00 UTC); the backend freezes its clock to the manifest's clock in mock mode so dossiers stay consistent whenever the demo runs. Live tests are backdated nine days; the Settings test ran 60 to 30 days ago. Per arm: purchases, trials, finished and converted trials (so `active_trials_rate` is real), refunds, payers, revenue per viewer, P2BB and the 99% range from a seeded normal approximation of revenue per viewer, p-value from the two-proportion test. Each variation carries ten per-day `values` points (installs of the day plus the money moved that day), a screen funnel and product nodes. Result: Onboarding 1,020 vs 975 viewers, 269 open trials, still WAIT_TRIAL_LAG with the leader flippable; Main NA 140 vs 156 viewers, NOT_DECIDABLE (2,402 per arm, 145 days away); Settings audit grade C, realized revenue reversed the call. Assumption: the per-day point shape (metric keys plus `x`) mirrors the analytics chart points; the captured lifetime answers have empty `values`, so the real daily shape was not observed.
- Iteration 3: synthetic tests. A test spec can now draw viewers from users of an existing flow, optionally one shard of them (user id modulo), and a flow can exist only in the expanded set (`SYNTHETIC_FLOWS`, written to `flows_list.json` with a stable id). Added "Main paywall: lifetime anchor vs 3 plans vs social proof": a live three-arm test on the Main placement for All users, running 90 days, control A = lifetime anchor users, B = half of the 3-plans users, C = the other half relabelled as the new "Main - Social proof" flow (same outcome distribution as B, different users, so B vs C is a genuine no-difference pair). Result: about 2,290 viewers per arm against 1,332 needed, A at 24% paid conversion vs 10% and 11%, Holm-adjusted p-values at zero, P2BB 100% for A: CALL_WINNER with the dry-run stop command. The placement now lists two audiences (NA segment test first, then this one). Also fixed the referee to measure paid conversion as paying users over viewers rather than purchases over viewers, which renewals would inflate on long-running tests.
- Iteration 4: measured traffic and payer rates per placement, flow and segment (table from a one-off script: win-back gets 16.7 users a day at a 13.5% payer rate, so a two-arm test there needs 2,730 viewers per arm and 326 days from zero; it can only ever be NOT_DECIDABLE on Lumen traffic). The WAIT_SAMPLE state therefore lives on the onboarding placement instead: "Onboarding EU: weekly first vs EUR prices" on the Europe Tier-1 segment (GB, DE, FR, NL, SE), weekly-first users split in two shards, the second relabelled as the new flow "Onboarding - Weekly first (EUR prices)", running 95 days. Result: 1,297 vs 1,263 viewers against 1,296 needed, sample reached on 10 Nov 2026, p-value 0.45, P2BB 37 vs 63: WAIT_SAMPLE with the decision two and a half days out, and an honest no-difference once it lands. Test specs gained `segment_key` country filters and `exclude_segments`; the All-users Onboarding test now excludes EU1 users because the segment audience takes them first (782 vs 764 viewers, 202 open trials, still WAIT_TRIAL_LAG). The store orders synthesized placement audiences with segment tests before All users, so the onboarding placement shows the EU test as priority 1.
- Iteration 5: two completed tests. "Onboarding NA: weekly first vs annual trial" (US and Canada, 120 to 60 days ago, control weekly first declared winner): 2,181 vs 2,177 viewers against 1,050 needed, 617 payers, p-value at zero, P2BB 100%, grade A, and the lifetime flow metrics confirm it (weekly first $7.99 per viewer on 13,798 views vs $4.27 for the trial). "Win-back: monthly vs annual offer" (Payers segment, five days, 45 to 40 days ago, the new "Win-back - Annual offer" flow declared winner on 3 payers): grade F with every deduction. The realized check now needs 200 views on both flows before calling confirmed or reversed, so this one and the captured one-day Settings audit read inconclusive, while the expanded Settings test (1,785 vs 6,852 views) still reads reversed. The three completed tests now show A confirmed, C reversed and F inconclusive. Opportunities rank the AI-limit draft first, then the idle Settings and Win-back placements.
- Iteration 6: `metrics get --group-by country` and `--group-by store` answers for all seven tests with metrics (14 trees, the set is now 47 files, 1.9 MB). Each variation splits into real segments from the users' country (15 countries, named as Adapty does, with the ISO code in `segmentation`) or platform (App Store, Google Play), and every segment carries its own screen funnel and product nodes, so the numbers add up exactly to the variation. P2BB fields on segment nodes are zero, as Adapty does not compute them per segment. The store serves them through `POST .../metrics/` with `segmentation_by`.
- Iteration 7: catalogue entities. Three placements ("Trial ending reminder" flow placement, "Export limit reached" paywall placement, an inactive "Holiday sale" paywall placement) so the Paywalls tab and the inactive state have content; two segments ("Churn risk", "Trial users"); a draft flow "Main - Holiday sale"; a product "Premium Annual (Holiday 30% off)" at $34.99; and a second draft test, "Win-back v2: annual offer vs monthly (churn risk)". Lists are now generated instead of copied: 8 placements, 5 segments, 8 products, 10 flows, 9 tests. The next-test ranking now puts idle placements with a ready draft first, then idle placements by revenue, then placements without traffic, then busy ones.
- Iteration 8: analytics generated from the same users. Revenue by week over 18 weeks ($441,902 in total) segmented by store product exactly as Adapty keys it (iOS products under their id and title, Android under the Play id) and, new, by flow after test relabelling; install-to-paid by month and flow (19.4% overall, 10.8% on the annual-trial onboarding, 26.0% on the lifetime anchor); trial-to-paid by month and product with finished trials in `value_from` and running ones in `value_from_unfinished` (45.0% on 7,821 finished trials: 36.5% for the 7-day annual trial, 49.1% for the 3-day weekly trial). The store now picks charts and conversions by `chart_id`/`conversion_id` plus `segmentation`. The referee uses the per-product rates: each arm's trial-to-paid estimate is the account's product rates weighted by the trial plans that arm's viewers actually started (read from the metrics tree), so the annual-trial arm no longer borrows the weekly plan's conversion.
- Iteration 9: verdict coverage and the default set. Added "Onboarding NA v2: weekly first vs annual anchor copy" (US and Canada, live for 69 days after the completed NA test, weekly-first users split in two shards, the second relabelled as "Onboarding - Weekly first (annual anchor)"): 1,228 vs 1,207 viewers against 1,121 needed, p-value 0.90, P2BB 77 vs 23: CALL_NO_DIFFERENCE, keep the control. The All-users Onboarding test now excludes both segments (460 vs 447 viewers, 85 open trials, still WAIT_TRIAL_LAG). Seven of the nine verdict codes appear in the set (WAIT_TRIAL_LAG, NOT_DECIDABLE, CALL_WINNER, WAIT_SAMPLE, CALL_NO_DIFFERENCE, COMPLETED, NOT_STARTED). WAIT_MIN_RUNTIME and INSUFFICIENT_PAYERS need a sample reached within a week or with under 50 payers, which Lumen's traffic never produces at the default 20% effect; both appear live in the UI by raising the planned minimum effect on a young test (for example 100% on the NA main paywall test). The trial-lag rule gained a materiality floor: open trials must be worth at least 5% of the leader's revenue before they block a call, so a near tie with a dozen open weekly trials is a no-difference question rather than a wait. `ADAPTY_FIXTURES` now defaults to `expanded`; the API tests pin `captured`. The metrics page's "Group by" control is wired: Country and Store fetch the breakdown tree and show one indented row per segment under each variant.
- Iteration 10: validation. 129 backend tests pass with the statistics at 100% branch coverage; two generator runs produce identical files (54 files, only `generated_at` differs); a route self-test on the expanded set makes 86 calls across every test, placement, flow, segment, product, analytics and referee endpoint with zero failures, template memos pass the number guard for all ten tests, and a proxied stop is refused with 403. Frontend type-check and production build pass.
